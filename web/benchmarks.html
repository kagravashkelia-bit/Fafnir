Measured, not marketed.

What this is notNPS is a throughput measurement, not a rating. Two engines with the same NPS can differ by hundreds of Elo because of search quality, evaluation and time management. Fafnir publishes speed here and regression results in the repository; it does not claim an Elo from either.

AVX2 is the practical choice

Most x86-64 CPUs from Haswell (2013) and Excavator (2015) onward support AVX2. It delivers 1.92× the SSE2 throughput in this test.

＋

AVX-512 adds a small step

The AVX-512 + VNNI build reaches 2.04× SSE2 here. Gains depend on the CPU's vector width and clock behaviour under load.

≈

SSE4.2 ≈ SSSE3 in this position

POPCNT helps many workloads but not this one enough to separate the two builds reliably; the medians differ by about 3%.

i
Variance is realThe medians were collected in interleaved rounds to reduce thermal bias. Individual runs ranged from 205k to 232k NPS on SSE2 and 404k to 464k NPS on AVX-512. A laptop CPU is not a laboratory instrument.

Methodology

Reproduce it in five steps.

  1. Build every architecture

    make all-arches -j8 writes bin/Fafnir-<arch>.

  2. Close everything else

    Benchmarks are sensitive to background CPU load. Use the same power profile and leave the machine idle.

  3. Send the same commands

    uci, isready, position startpos, go depth 20. Default Hash and Threads.

  4. Read the final info line

    The last info depth 20 line gives nodes, NPS and time. Ignore the ponder move.

  5. Interleave and repeat

    Run each build in a different order, at least three times, and report the median.

Fixed-depth benchmarkbash
# Linux / MSYS2
make all-arches -j8

for arch in x86-64 x86-64-ssse3 x86-64-sse4.2 x86-64-avx2 x86-64-avx512; do
  printf 'uci\nisready\nposition startpos\ngo depth 20\nquit\n' \
    | ./bin/Fafnir-$arch
 done
Single buildpowershell
# Windows PowerShell
make all-arches -j8

"uci`nisready`nposition startpos`ngo depth 20`nquit`n" |
  .\bin\Fafnir-x86-64-avx2.exe
i
No hidden benchmark modeThe engine has no bench command. Use the UCI sequence above so the result is comparable with the table on this page.
Caveats

What can move these numbers.

Compiler and flags

The project builds with -O3, LTO and gc-sections. A different compiler version, a different standard library, or PGO can shift throughput. CI validates g++ on Linux and Windows; other compilers are accepted but not covered.

Thermals and power limits

A thin laptop can lose 15–25% NPS after a few minutes of sustained search. The interleaved medians above are an attempt to reduce that bias, not to eliminate it.

Hash size and position

Larger hash tables reduce re-search on long games but do not change raw NPS much. Tactical positions with many captures can hit different evaluation paths; startpos is a convention, not a universal proxy.

Operating system

Windows and Linux use different schedulers and C runtimes. The published archives are built by GitHub Actions on each platform; compare numbers within one OS.

Want the correctness numbers too?

The EPD suite measures move quality on 100 positions, with a strict best-move hit rule.
