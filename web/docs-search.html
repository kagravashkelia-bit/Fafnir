Search internals

How Fafnir searches: transposition table, six history families, MovePicker stages, pruning, LMR, time management and Aggressivity.

Fafnir 2.0Updated 2 November 2026Reference

The search lives in src/engine/search.hpp, with the move picker in movepicker.cpp and the thread controller in SearchController.cpp. The implementation follows the Stockfish development style; the constants and code are part of this repository, not a dropped-in binary.

Search pipeline

  1. Root setup. The controller copies the position, clears per-search state, and starts the requested number of threads.
  2. Iterative deepening. Depth increases one ply at a time until a limit is reached.
  3. Move generation. The MovePicker yields moves in stages, cheapest and most promising first.
  4. Pruning and reduction. Futility, null move, ProbCut, LMR and singular extensions decide how much work each node deserves.
  5. Evaluation. The NNUE probe returns a quantized score for the leaf.
  6. Backup. Scores and principal variations are stored in the stack and the transposition table.

Transposition table

The table is divided into clusters of three entries. Each entry stores a key fragment, a move, a score, the search depth and generation metadata. Replacement is age-based: an entry from an older search is evicted before a current-generation entry of similar depth.

Hash is exposed as a UCI spin option from 1 to 1024 MB, default 16. The implementation resizes the table immediately, so a GUI can change it between games without restarting the process.

History heuristics

Fafnir maintains the full family used by the reference search style:

HistoryPurpose
Main historyQuiet-move success by side, from, to and piece
Low-ply historyExtra weight for quiet moves near the root
Capture historyCapture success by piece and target
Continuation history (2×2)Success conditioned on the previous two moves
Pawn historyQuiet-move success keyed by pawn structure
Correction historyCorrects static evaluation bias by pawn / minor / non-pawn / continuation context
i
Correction historyCorrection history is not a tie-breaker. It adjusts the static evaluation before search uses it, which is why the four tables (pawn, minor, non-pawn, continuation) are updated separately.

MovePicker stages

StageContentsOrdering
TT moveHash move from the transposition tableExact match
Good capturesCaptures that pass SEEMVV-LVA, then SEE
QuietsAll remaining quiet movesMain / continuation history
Bad capturesCaptures that lose material by SEEMVV-LVA
Bad quietsDeferred quiet movesHistory
EvasionsLegal replies to checkTT, captures, history
ProbCutTactical subset at reduced depthSEE and capture gain
QsearchCaptures and promotions at the horizonMVV-LVA / SEE

The picker is stateful: each call to the next-move function advances through the stages and returns the next candidate without regenerating the full move list.

Pruning and reductions

TechniqueRole
RazoringDrop clearly hopeless nodes before full search
Futility pruningSkip quiet moves when the static score is far below alpha
Null-move pruningSearch a pass position to prove a beta cutoff, with verification
IIRReduce the depth when no TT move is available
ProbCutProbe a reduced-depth tactical search for a likely cutoff
Singular extensionExtend a move when it appears to be the only good reply
MulticutCut when several moves fail high in a reduced search
Negative extensionsReduce moves that repeatedly fail to improve
LMRReduce late quiet moves, with shallow re-search when they beat alpha

LMR at non-PV nodes uses both quiet history and futility to decide the reduction. A reduced move that returns a score above alpha is re-searched at full depth before it can change the principal variation.

Draw and repetition detection

SEE is computed with pinned pieces taken into account, so a capture that looks winning but exposes the king is not treated as a good capture. Cuckoo keys detect imminent repetition without walking the entire history. Repetition and the fifty-move rule are checked in the search stack before a node is searched.

Time management

The controller translates UCI limits into a soft and a hard deadline. movetime sets both to the same budget; clock-based searches derive an allocation from wtime/btime, increments and movestogo. Move Overhead is subtracted as a safety margin. ponder starts a search that can be stopped by the GUI.

Aggressivity

Aggressivity ranges from 0 to 100 and modulates the optimism applied to evaluation during search. At 0 the engine uses its default evaluation; higher values bias the search toward positions with more apparent activity. It is a search-time adjustment, not a separate evaluation function, and it does not change the network.
